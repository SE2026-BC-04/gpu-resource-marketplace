# CR-GPU-004-D7-01 — DB-managed Listing updated_at

**Status: PROPOSED / NEEDS_OWNER_DECISION — 2026-10-25.**
**Class: L2.** Requester/implementer: TV4; persistence owner/mandatory technical reviewer: TV2.

## Authority and problem

[The owner delegated R1 to TV4](https://github.com/SE2026-BC-04/gpu-resource-marketplace/pull/17#issuecomment-6396462023), but explicitly did **not** approve D7 DDL/schema/grant changes. This document requests that separate design decision. It does not authorize a migration or trigger implementation.

Baseline: `main@ce99293`, migrations through `0002_phase1b_grants`. Database Design v0.4 §9.2-06 requires DB timestamps; §11 requires READ COMMITTED and Listing-first locking. GPU-002-A §7 proposes `trg_gpu_listings_guard_update`; its D7 is not an accepted implementation decision. API §7 and the GPU-004 ports require updated metadata to use the approved DB-clock mechanism.

The existing INSERT defaults initialize both timestamps. UPDATE grants allow API metadata/status and future Manager allocation writes, but neither role can write `updated_at`. There is no Listing touch trigger on this baseline. An adapter must not grant itself timestamp access, use an owner connection, or pretend the old timestamp records the change.

## Proposed decision (Listing table only)

1. Add one owner-managed migration with a `BEFORE UPDATE FOR EACH ROW` trigger named `trg_gpu_listings_guard_update` on `public.gpu_listings`.
2. Reject changes to `id`, `worker_id` or `created_at` with a stable constraint error. Ownership remains immutable for all callers.
3. For **every executed UPDATE**, including a SQL no-op and future Manager allocation updates, overwrite `NEW.updated_at` with PostgreSQL `clock_timestamp()`. The API service already avoids issuing no-op metadata/status updates. Do not promise monotonic wall time or change `created_at`.
4. Use a small `SECURITY INVOKER` trigger function with a fixed `pg_catalog` search path and fully qualified clock call. It performs no queries or writes to other tables. Revoke the function's default PUBLIC EXECUTE privilege; verify restricted-role trigger execution on PostgreSQL 16 without adding runtime privileges.
5. Preserve D1 column grants. API still cannot UPDATE allocation, owner IDs or timestamps; Manager grants and behavior remain unchanged apart from the DB-managed touch on its future Listing UPDATEs. Do not extend this CR to reputation, Jobs D2/D3 or other tables.
6. Select the new Alembic revision/down_revision against the actual accepted migration head **after approval**, to avoid colliding with pending D2/D3 revisions. Do not rewrite old migrations or stamp/downgrade an existing database to install this change.

Alternative A: keep the current schema; read/create can run, but metadata/status writes remain blocked until a DB-clock mechanism is approved. Alternative B (not recommended): grant callers timestamp writes/use an owner connection; this weakens D1 and is outside the delegated scope. Proposed trigger preserves the existing access boundary.
