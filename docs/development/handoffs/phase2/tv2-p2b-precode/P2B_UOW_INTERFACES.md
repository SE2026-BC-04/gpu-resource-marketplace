## 1. Contract common to every port (`B-IF-09` part)

1. **One logical transaction = one UoW = one `Session`**, created and closed inside one synchronous executor call. No `await` while a UoW is open. Repositories take the `Session`/connection and never commit.
2. **Native identity check on entry**, same pattern as `repositories/jobs.py`: `current_user` ∈ the role's group/login set **and** `session_user` = the native login (`gpm_manager_app` for Manager ports, `gpm_api_app` for ingress), isolation `READ COMMITTED`, no owner session, no `SET ROLE` outside tests. The existing allow-lists are API-only; Manager ports get their own parameterized guard rather than loosening the API one.
3. **Lock order** (global, `database-design.md` §11.1): `gpu_listings → jobs → allocations/attempt → result_inbox (ordered received_at,id) → job_reputation_contributions → worker_reputation_aggregates`. **Decision D-18 (lead `APPROVED_DESIGN_DIRECTION_CONDITIONAL` @ `531805b`, an L2 supersession; exact-SHA TV3/TV4/TV5 ACKs pending): a new first position, the per-Worker advisory lock** (`Worker (advisory) → gpu_listings → jobs → …`), taken only by `TX-ALLOCATE` (shared) and by Worker key registration/activation (exclusive); see B-IF-06. No other transaction takes it, so it cannot form a cycle, but it changes the global order in `database-design.md` §11.1; that source document and the others listed in `OPEN_DECISION_REGISTER.md` §0.2 must be reconciled before migration. Outbox transactions lock the Outbox row only. Locators (listing id for a job id) are unlocked reads, rechecked under lock. Never `SKIP LOCKED` on a Job head. Never take an Inbox row lock and then wait for Listing/Job.
4. **Clock:** every business timestamp is `clock_timestamp()` read **after** the locks it depends on, inside the transaction. Tests use a trusted test clock function, never `sleep`.
5. **Commit outcome:** classify with `commit_outcome.is_definite_commit_rollback`. Definite rollback ⇒ typed `Rolled back` result; `40003`, lost connection or unknown code during `COMMIT` ⇒ `CommitOutcomeUnknown`, **never retried blindly**: the caller (TV1) calls the port's `reconcile_*` read, which decides from DB state. Whole-UoW retry only for `40001`/`40P01` with a finite budget and **stable identifiers** (same `attempt_id`, `event_id`, `result_id`).
6. **Outcomes and errors.** Business outcomes (`Noop`, `Blocked(reason)`, `Conflict`, `Ineligible`, `StaleClaim`, `Stored`, `Allocated`, …) are **returned values**, produced only after the UoW has committed (no-op/blocked paths COMMIT with no writes, `database-design.md` §11.3 A) or rolled back and the `Session` is closed; they are never raised inside an open transaction. Exceptions are for `DependencyUnavailable`, `CommitOutcomeUnknown` and programming errors. All are secret-free and raised `from None`. No DSN, SQL, bytes, token or key in a message or log.
7. **No network I/O, no waiting on another task, no logging of payload bytes** while a UoW is open.

## 2. The nine interfaces

### `B-IF-01` — TV1 ↔ TV2: baseline and activation preflight
Provides: accepted `main` SHA, Alembic head, expected native roles/grants, a read-only `phase2_ready()` probe (R1 tables present, R2 grants match the checked-in expectation, two guard triggers installed) usable at Manager startup. Fail closed: not ready ⇒ Phase 2 loops do not start. Separate from `/health/ready` (Phase 1 readiness is not widened without the owner's L2 decision). Status: `PENDING_BASELINE`.

### `B-IF-02` — TV2 ↔ TV3 ↔ TV5: duplicate and collision semantics
`ingest_signed_result(raw: bytes, ctx: UntrustedContext, listing_hint: UUID) -> Stored(inbox_id, received_at) | ExactDuplicate | Collision | Ineligible(reason) | CommitOutcomeUnknown`.
Pre-conditions (outside the UoW, TV3): service token valid and direction correct, body within bound, envelope parses, claimed ids are UUIDv4. Inside: Listing → Job lock; probe (`INBOX_DUPLICATE_PRIVILEGES.md`); recheck Job `RUNNING` and the current attempt; insert with `RETURNING id, received_at` and require the **stored** `received_at < hard_deadline_at` (equality is late), otherwise roll back as `Ineligible(late)`. The late check runs **immediately after `RETURNING`, before any other write**, and the rollback covers the whole UoW (no Outbox event, no audit row, nothing else); `hard_deadline_at` is the value read from the attempt row **locked in this UoW**, never from the callback body (one instant for the test and the stored value, see `INBOX_DUPLICATE_PRIVILEGES.md` §4 item 5). HTTP mapping, names from API Contract §13.2 (TV3 review):

| Port result | HTTP | Persistence |
|---|---|---|
| `Stored`, `ExactDuplicate` | `202` | row stored / unchanged |
| `Collision` (port name; includes `DIFFERENT`) | `409 RESULT_ID_COLLISION` | none |
| `Ineligible(unbound)` | `404 RESULT_CONTEXT_NOT_FOUND` | none, redacted log |
| `Ineligible(not_running)`, `Ineligible(late)` | `409 RESULT_NOT_ACCEPTABLE` | none, redacted log |
| `DependencyUnavailable`; `CommitOutcomeUnknown` the probe cannot reconcile | `503` (sender retries, ADR-005; no false durable success) | none claimed |

Body bound, JSON depth and every parse failure (`422 INVALID_SIGNED_ENVELOPE`) belong to TV3 before the UoW (D-07: TV3 proposes 16,384 raw bytes inclusive and at most 4 JSON levels, pending TV1 + TV5 ACK; TV5 agrees and asks for `Content-Length` plus streamed enforcement and boundary tests 16,384 vs 16,385, depth 4 vs 5, chunked/incorrect length). Unauthenticated or unparseable input never reaches the UoW.

Collision and duplicate rules (D-02, TV5 review): `INSERT ... ON CONFLICT DO NOTHING RETURNING id, received_at` with **no explicit conflict target** (an explicit `(result_id) WHERE ...` target would need `SELECT(result_id)`, which option B/A does not grant; `INBOX_DUPLICATE_PRIVILEGES.md` §4 item 3); zero rows means a conflict, followed by a **fresh probe statement** that covers the same-Job and the cross-Job case (same `result_id`, other Job or attempt ⇒ `Collision`, nothing overwritten). A duplicate that arrives after the Job is terminal is still `202` when the row is retained (`ExactDuplicate`, no new effect); once the row is purged the answer is a Phase 3 retention matter, not decided here. An unknown `COMMIT` is reconciled in a **new** transaction by the probe, never by re-inserting.

Rows that are stored: only a structurally valid, context-bound, on-time receipt is stored, as `PENDING`. It may later become `REJECTED` (reason code only) after TV3's signature verification inside finalization. That is different from the D-08 rule "no *unbound* rejected row": `401/404/409/422` store nothing and write only a redacted structured log.

### `B-IF-03` — TV2 ↔ TV3: restricted raw comparison
The probe path, grants and the SHA-256 vs function decision are in `INBOX_DUPLICATE_PRIVILEGES.md`. The port exposes only `ABSENT | SAME | DIFFERENT`; it never returns stored bytes.

### `B-IF-04` — TV2 ↔ TV3: `received_at` and trusted identity
`received_at` is a column default `clock_timestamp()` evaluated on insert after the Job lock; the API has no INSERT grant on it, and reads back only `id` and `received_at` through `RETURNING` (column `SELECT` on those two) so the deadline test uses the stored instant, not a second clock read. Identity of the caller is the Simulator service token handled by TV3; the worker/listing identity comes from the locked Job row, never from the body. A replay never rewrites `received_at`.

### `B-IF-05` — TV1 ↔ TV2 ↔ TV3 ↔ TV5: candidates, batches, progress
`iter_eligible_inbox(job_id, cursor: (received_at, inbox_id) | None, bound: int) -> Batch(candidates, has_more, scanned_through)`. Order `(received_at, id)`, only `state='PENDING'` and `received_at < hard_deadline_at`. It is a **read for the verifier** (unlocked locator read); it grants nothing. `has_more=True` forbids fallback. The cursor is data, so a restart resumes. After a terminal commit a housekeeping call marks remaining non-winner rows `REJECTED` (reason `NOT_SELECTED`/`ALREADY_TERMINAL`) without any business effect.

**Earliest-winner is enforced by persisted state, not by whichever finalizer locks first (TV5 blocker A).** The "first verified, context-eligible candidate in `(received_at, id)` order wins" rule lives in the write ports:
- `reject_candidate(job_id, rejected: RejectedV1Receipt) -> Rejected | AlreadyDecidedNoop | BindingMismatchNoop | CommitOutcomeUnknown`: Listing → Job → that Inbox row; after the locks the port rechecks that the row is still `PENDING`, that `rejected.inbox_id` is the row id, that its stored `result_id` equals `rejected.result_id`, that its stored `envelope_sha256` (and `sha256(original_envelope_raw)`) equals `rejected.envelope_sha256`, and that its bound Job and attempt equal both the locked ones and `rejected.job_id` / `rejected.attempt_id`; only then it sets `REJECTED`, `rejection_code`, `processed_at`; no business effect. A verdict for another row or other bytes is `BindingMismatchNoop` and changes nothing, so a stale or mismatched verifier result can never reject a different valid `PENDING` candidate or shrink the scan toward a false `SYSTEM_FAULT`. Callable while the Job is `RUNNING` or already terminal. Only a **definitive** verification failure from TV3 may use it, and its `rejection_code` must be one of the **four** codes that are definitive after ingress admission: `UNKNOWN_KEY` (no registered `(worker_id, key_id)`), `KEY_WORKER_MISMATCH`, `CONTEXT_MISMATCH` (signed Job/Attempt/Worker/Listing differ from the bound context), `INVALID_SIGNATURE` (closed enum, TV3 proposal in PR #49, `PROPOSED_FOR_ACK`). A parse or schema-version failure on bytes that ingress already admitted is an **invariant break**, not a verdict: `INVALID_STRUCTURE` and `UNSUPPORTED_SCHEMA_VERSION` are therefore **not** valid codes (TV2 choice offered by TV3: removed from the enum and from `ck_result_inbox_rejection_code`, nothing migrated yet), a `RejectedV1Receipt` carrying anything outside the four is refused, and the row stays `PENDING` (fail closed, blocks fallback). The housekeeping codes `NOT_SELECTED` and `ALREADY_TERMINAL` are **not** verifier verdicts: they are written only by TV2's housekeeping call and a `RejectedV1Receipt` carrying one is refused. `ck_result_inbox_rejection_code` (schema matrix §5) enforces the union of both sets in the database. A transient failure (key store unavailable, `DependencyUnavailable`) changes **nothing** and leaves the row `PENDING`, which blocks fallback (see B-IF-07).
- `finalize_one` (below) refuses a candidate while any earlier `PENDING` on-time row exists for the Job: the check is a statement under the Listing → Job locks, `NOT EXISTS (… bound_job_id = :job AND state='PENDING' AND received_at < hard_deadline_at AND (received_at, id) < (:cand_received_at, :cand_id))`. It answers `PrecedingPending(first_pending_cursor)` with no change, so the caller verifies and settles the earlier row first. Therefore invalid-first / valid-second works for any batch size (bound = 1 included): the invalid row is `REJECTED` by `reject_candidate`, then the valid row passes the check; and skipping an earlier row is impossible even with two consumers, whichever locks first.
- Ingress for one Job is serialized by the same Job lock and `received_at` is read inside it, so a row committed before the finalizer holds the Job lock is visible to the check (READ COMMITTED, new statement). Assumption stated, not hidden: the DB wall clock does not step backwards between two inserts; if it does, the stored order is still the order used, and a candidate may answer `PrecedingPending` for a row that arrived later with a smaller `received_at` (safe direction).

### `B-IF-06` — TV1 ↔ TV2 ↔ TV4 ↔ TV5: allocate and Outbox
- `allocate_one_listing(listing_id, signer: SignerReadiness) -> Allocated(job_id, attempt_id, event_id) | Blocked(reason ∈ LISTING_NOT_ACTIVE, HEAD_DOES_NOT_FIT, SIGNER_NOT_READY) | Noop(reason ∈ NO_QUEUED_HEAD, LISTING_NOT_FOUND, LOCK_BUSY) | CommitOutcomeUnknown(listing_id, job_id, attempt_id, event_id)`. Cleanup per outcome: `NO_QUEUED_HEAD` and `HEAD_DOES_NOT_FIT` COMMIT a no-op (nothing written, locks released) and the value is returned after the UoW closed; `LISTING_NOT_ACTIVE` (including a missing-status Listing) the same; `LISTING_NOT_FOUND` (locator read or lock finds no row) rolls back and returns; `LOCK_BUSY` (`55P03` from `lock_timeout` on the Listing or head) rolls back, writes nothing, and the scheduler retries on its next pass (no head bypass, no counter change). Known ids for unknown-`COMMIT` reconciliation: under P1 `attempt_id` and `event_id` are chosen before the first statement and the locked head's `job_id` is known after the lock, so `CommitOutcomeUnknown` carries all four; the caller reconciles with `reconcile_allocation(job_id, attempt_id) -> AllocationCommitted(job_id, attempt_id, event_id, job_status, allocation_state) | AllocationNotCommitted | AllocationUnknown` (a read, never a mutation). It decides from the **durable graph**, not from the Job's current status: the commit happened iff the `execution_attempts` row for that `job_id` (and `attempt_id` under P1) exists, together with its `allocations` row and `execution_outbox` row. A Job that is already `COMPLETED`/`FAILED` and an allocation already `RELEASED` are the legitimate consequences of that same commit (lost ACK, then another Manager finalized before the reconcile) and still answer `AllocationCommitted` with the ids, so the caller neither re-allocates nor reserves again nor reports a rollback. `AllocationNotCommitted` requires the **absence** of the whole graph **and** the Job still `QUEUED` (nothing advanced); a partial or contradictory graph, or a Job that moved on with no attempt row, is `AllocationUnknown` (escalate, no retry), never a rollback inferred from a state that has advanced. Under P2 only `listing_id` and `job_id` are known and reconcile reads the attempt by `job_id` and returns the DB-chosen ids. Locator read of the Listing's `worker_id`; shared Worker advisory lock (D-18); lock Listing and recheck `worker_id`; require `ACTIVE`; require exactly one active Worker key (else `Blocked(SIGNER_NOT_READY)`); select the real FIFO head `ORDER BY enqueue_seq LIMIT 1 FOR UPDATE` (no `SKIP LOCKED`); if `total - allocated < head.requested` return `Blocked`, **never** a smaller later Job; `t = clock_timestamp()` after both locks; guarded counter update (`allocated + n <= total`); Job `QUEUED→RUNNING` with `started_at = t` (`WHERE status='QUEUED'`, row count must be 1); insert `allocations`, `execution_attempts` (`finish_due_at = t + duration`, `hard_deadline_at = finish_due_at + 120 s`), `execution_outbox` (stable `event_id`, immutable payload, see the payload contract below). One COMMIT. FIFO policy inputs (eligibility, fairness) come from TV4 as data; the port does not choose a different head.
- **Per-Worker serialization and signer readiness (D-18; answers TV3 PR #49 §6.4/§6.6.5 `C-IF-08` and TV4 PR #48 `D-IF-07`; `PROPOSED_FOR_ACK`).** Allocation must not start a new attempt for a Worker whose signing key is being rotated, and key rotation must not retire a key while an attempt that needs it is `RUNNING`. No new table, status or grant:
  - **Lock.** A transaction-scoped advisory lock keyed by the Worker: `pg_advisory_xact_lock_shared(hashtextextended('gpm:worker-key:' || :worker_id, 0))` in `TX-ALLOCATE`, `pg_advisory_xact_lock(...)` (exclusive) in key registration and activation. Advisory lock functions are executable by `PUBLIC`, so no grant changes; a hash collision only causes false waiting, never a wrong result. Native-role `EXECUTE` is proven as `gpm_manager_app` and as the provisioning identity (S-10 / D-03, not decided here).
  - **Position.** First, before the Listing lock: `Worker (advisory) → Listing → Job → Allocation → Inbox → …`. `TX-ALLOCATE` reads `gpu_listings.worker_id` in its unlocked locator step (the D7 identity guard makes it immutable), takes the shared Worker lock, then locks the Listing and **rechecks `worker_id`** (mismatch ⇒ `Noop(LISTING_NOT_FOUND)`-class rollback). Submit, Cancel, Pause, Resume, Listing create, Finalize and Inbox ingress never take the lock. The lock is waited on with the same `lock_timeout` as the Listing lock and `55P03` is `Noop(LOCK_BUSY)`.
  - **Proof identity is part of the locked predicate (TV5 TOCTOU finding, `PROPOSED_FOR_ACK`).** The key count alone lets a Manager that cached a valid proof for K1 allocate after K2 was activated (one active row, K2) on a stale K1 proof. So the internal typed port takes `signer: SignerReadiness(worker_id, key_id, public_key_fingerprint, proof_expires_at)`, produced by the live-signer gate (#49 §6.6.5 item 9; the exact fields are frozen with TV1/TV3/TV5; under G2 the gate supplies the same identity from its own check). Under the Worker advisory + Listing locks, `TX-ALLOCATE` requires that the **sole** active `worker_public_keys` row has `key_id = signer.key_id`, a matching fingerprint of `public_key_raw`, `signer.worker_id` equals the Listing's Worker and `clock_timestamp() < signer.proof_expires_at`; any mismatch or expiry returns `Blocked(SIGNER_NOT_READY)` (COMMIT a no-op: FIFO, GPU counter, Job and Outbox untouched). The Manager also drops its cached readiness on key activation or at TTL expiry. **Fingerprint algorithm (proposal for TV3's `PENDING_ACK`):** `public_key_fingerprint` is the 64-character lowercase hexadecimal SHA-256 of the 32 raw public-key bytes, i.e. `encode(sha256(public_key_raw), 'hex')` in PostgreSQL (the built-in `sha256(bytea)`, no extension) and `hashlib.sha256(public_key_raw).hexdigest()` in the Manager; no domain prefix, no base64, no key-id mixed in. The DB compares it to the locked row with `encode(sha256(public_key_raw), 'hex') = :fingerprint`; the test asserts both sides produce the same value for the same key (known-answer vector from TV3). The fingerprint only detects which key a proof was made for; it is not a secret and not a signature. This is an **internal** port argument only: it adds nothing to the ten-key dispatch body or to any table, and it is never written to the database.
  - **Signer-ready rule.** After the locks, `TX-ALLOCATE` reads `worker_public_keys` for the Worker; unless **exactly one** row has `retired_at IS NULL` it returns `Blocked(SIGNER_NOT_READY)` (COMMIT a no-op, nothing written, the head stays `QUEUED`, FIFO unchanged). Phase 1 has no partial unique index on the active key, so **two active rows are the quiesce marker**: registering K2 while K1 is active makes allocation for that Worker fail closed. Do **not** add a unique index for the active key (it would remove the marker); a bug that leaves two active rows fails closed, not open.
  - **Rotation sequence (documents the use, TV3 owns the key policy).** (1) under the exclusive lock, register K2 (two active rows; waits for in-flight allocations, which hold the shared lock until commit); (2) drain `RUNNING` attempts of that Worker; (3) deploy K2 to the Simulator and self-check; (4) under the exclusive lock, recheck that no `RUNNING` attempt exists for the Worker, then set `retired_at` on K1 (one active row again, allocation resumes). K1 receipts stay verifiable from the retained row. Activation aborts, writing nothing, if a `RUNNING` attempt exists.
  - **Conflict with the approved source (TV5 action A; lead L2, TV3 `E-C3`).** `database-design.md` §9.2-05 and `phase1b_gpu002a_schema_matrix.md` (`uq_worker_public_keys_active_worker`, D4 "needs confirmation") *propose* `UNIQUE (worker_id) WHERE retired_at IS NULL`. The implemented baseline (`domain/identity.py`, `0001`) has **no** such index, so two active rows are possible today. If the lead approves the two-row marker, that index must never be created and the approved source, Phase 2C and these docs are reconciled by SHA; if the lead keeps the index, K2 cannot be registered while K1 is active and D-18 needs a different quiesce marker (TV2 does not choose). Until then D-18 is a conditional direction and TV2 adds no index, migration or grant for it.
  - **DB key count is necessary, not sufficient (TV5 action B).** "Exactly one active key" proves only the registry, not that the live Simulator holds the matching private signer. TV2 states the prerequisite and does not implement it: a trusted provisioning-time and Simulator-startup check of the private key against the registered public key, and a fail-closed operational gate in the Manager (Phase 2 loops do not start allocation for a Worker whose signer is unverified, including after a Simulator restart or a lost/mismatched K2 after step 4). **One gate, named in one place: TV3's PR #49 §6.6.5 item 9** (G1 proof of possession: a nonce signed under the separate `GPU-MARKETPLACE:SIGNER-PROOF:V1
` prefix and verified against the single active key, outside any UoW, needs an internal endpoint and therefore change control; or G2 dispatch refusal; Manager-memory readiness with a TTL, fail closed on Manager restart; the lead selected **G1** (do not confuse it with the G1 coding gate); G2 is not selected; readiness is also invalidated on key activation, expiry, Manager restart and known signer lifecycle changes; TV1/TV3/TV5 still document proof replay protection, nonce freshness, TTL, timeout, Simulator restart inside the TTL and unavailable-signer recovery, and the L2 API Contract change for the internal endpoint is required). TV2 owns no part of it. The scheduler's only requirement: a Worker without a fresh proof is **not passed** to `allocate_one_listing`, a Worker with a proof passes its `SignerReadiness`, and the outcome category is the same `Blocked(SIGNER_NOT_READY)` (the under-lock check above is the safety net, the scheduler pre-filter is only an optimization). The gate is evaluated **outside** any open UoW: no HTTP while holding the advisory or any row lock, and the Simulator gets no DB credentials. A `SIGNER_NOT_READY` from that gate and from the key count use the same typed `Blocked` outcome.
  - **Atomic activation (TV5 action C).** Activation runs under the exclusive Worker lock and rechecks, in one transaction: the active rows are **exactly the expected pair** `{K1, K2}` (expected `key_id`s passed in by the provisioning caller; a third key or a partial registration fails closed and writes nothing), the trusted K2 self-check result is present, and no `RUNNING` attempt exists for the Worker; then it sets `retired_at` on **K1 only**. Abort/rollback after a failed K2 deployment runs under the same exclusive lock, leaves exactly K1 usable and keeps (or restores) the Simulator's K1 signer **before** the allocation fence is removed (K2 row retired under the lock, one active row again).
  - **Cost (TV5 action D).** Shared holders do not block each other; an exclusive holder blocks new allocations for that Worker only, and only for the registration/activation transaction (short, no network I/O). Scheduler fairness and Manager pool sizing must account for allocations of one Worker waiting on `lock_timeout` (`Noop(LOCK_BUSY)`, retried next pass); numbers stay `PENDING_PARAMS` in `RUNTIME_BUDGET.md`, no budget claimed as PASS.
  - **Not decided here:** which identity writes `worker_public_keys` (the Manager has only `SELECT`; D-03 / S-10), compromise policy, the numeric `lock_timeout`, and the lead's disposition of `E-C3`.
- **Dispatch payload contract (D-05 / D-13, TV5 blocker; proposal P1, fallback P2 below).** The Manager→Simulator POST body has **exactly ten keys**: `outbox_event_id, job_id, attempt_id, worker_id, listing_id, gpu_count, duration_seconds, simulation_input, finish_due_at, hard_deadline_at`, with `simulation_input = {"workload_profile":"demo-v1"}`. Never present: `simulation_references`, seed, expected outcome, key, token, any oracle value.
  - **P1 (APPROVED by the lead, conditional, @ `531805b`): `execution_outbox.dispatch_payload` stores all ten keys, immutable.** `outbox_event_id` is the row's `event_id` (same value). To have both ids inside the NOT NULL payload at the first and only INSERT, the UoW generates `attempt_id` and `event_id` (UUIDv4) in the Manager process **before** the first statement (outside any retry loop, so a `40001` retry reuses them) and inserts them explicitly. This needs column grants `INSERT(attempt_id)` on `execution_attempts` and `INSERT(event_id)` on `execution_outbox` (the D-13 answer: caller-chosen, two column privileges, PK/unique constraints still apply). No later UPDATE ever touches the payload (the Outbox `U(...)` list does not contain it).
  - Timestamps: the UoW reads `t = clock_timestamp()` once after the locks and derives `finish_due_at = t + duration` and `hard_deadline_at = finish_due_at + 120 s` from that single value (one statement, no second clock read). The same values are written to the columns and, as UTC RFC 3339 strings with 6 fractional digits and a `Z` suffix, into the payload. Strings are stored as jsonb strings and are never re-parsed or reformatted.
  - DB guard `ck_execution_outbox_payload_shape` (proposed): a CHECK accepts TRUE **or NULL**, so the whole predicate is wrapped as `COALESCE((<predicate>), false)` and the id keys are required to be JSON strings; a JSON `null` id (`->>` yields SQL NULL) or a missing key therefore fails. `<predicate>` = `jsonb_typeof(dispatch_payload) = 'object' AND dispatch_payload ?& ARRAY[<ten keys>] AND (dispatch_payload - '<k1>' - … - '<k10>') = '{}'::jsonb AND jsonb_typeof(dispatch_payload->'outbox_event_id') = 'string' AND jsonb_typeof(dispatch_payload->'attempt_id') = 'string' AND dispatch_payload->>'outbox_event_id' = event_id::text AND dispatch_payload->>'attempt_id' = attempt_id::text AND dispatch_payload->'simulation_input' = '{"workload_profile":"demo-v1"}'::jsonb`. Cross-table equality (`job_id`, `worker_id`, `listing_id`, `gpu_count`, `duration_seconds`, the two timestamps vs `jobs`/`execution_attempts`) cannot be a CHECK; it is a transaction rule with a test.
  - **Serialization (jsonb does not keep key order or whitespace).** The dispatcher never sends `dispatch_payload` as PostgreSQL printed it. It builds the body with one deterministic function `canonical_dispatch_body(payload) -> bytes`: UTF-8, keys sorted, separators `(',', ':')`, no non-ASCII escaping surprises (all values are ASCII), integers as JSON integers. A resend after a lost ACK, a stale-lease takeover or a restart produces **byte-identical** bytes. TV1 owns the function and the HTTP side; TV2 owns the stored value and the key set.
  - **P2 (not selected; kept only as the record of the alternative):** `dispatch_payload` stores an immutable eight-key core (everything except `outbox_event_id` and `attempt_id`); the two primary keys, `execution_attempts.attempt_id` and `execution_outbox.event_id`, keep their DB defaults (no `INSERT(attempt_id)` on attempts, no `INSERT(event_id)` on the Outbox). `execution_outbox.attempt_id` is still inserted explicitly because it is the NOT NULL foreign key without a default (it comes from `INSERT ... RETURNING attempt_id` of the attempt row). `claim_due_outbox` returns both ids from the columns, and the same `canonical_dispatch_body` adds them. Cost: the payload column alone is not the wire body, so the shape CHECK covers eight keys and the join to columns is part of the contract.
  - Tests (new `P2B-DRT-18`): exact key set; none of the forbidden keys; `outbox_event_id = event_id`; payload unchanged after claim/ack/retry; `canonical_dispatch_body` bytes identical across claim, stale takeover and resend; a payload with 9 or 11 keys, a wrong profile or a non-object is rejected by the CHECK.
- `claim_due_outbox(batch_limit, owner) -> list[FencedClaim(event_id, attempt_id, payload, observed_lease_version)]`: Outbox-only, no Listing/Job lock, HTTP after COMMIT. Exact predicate (P1-01, lead review): one `UPDATE execution_outbox SET state='CLAIMED', lease_owner=:owner, lease_until=:now+lease, lease_version=lease_version+1, updated_at=:now WHERE event_id IN (SELECT event_id FROM execution_outbox WHERE (state='PENDING' AND next_retry_at <= :now) OR (state='CLAIMED' AND lease_until <= :now) ORDER BY next_retry_at, event_id LIMIT :n FOR UPDATE SKIP LOCKED) AND ((state='PENDING' AND next_retry_at <= :now) OR (state='CLAIMED' AND lease_until <= :now)) RETURNING ...` (`SKIP LOCKED` is allowed here only because rows are independent deliveries; it is never used on a Job head). An expired lease is claimable **only when `state='CLAIMED'`**. `ACKED` and `EXHAUSTED` rows are **never** claimed by this port, whatever `lease_until` says (it is NULL for them anyway, see CHECKs).
- `ack_or_retry(event_id, observed_lease_version, owner, response_class) -> FencedUpdated | StaleClaimNoop | CommitOutcomeUnknown`. Every transition is one `UPDATE … WHERE event_id=:id AND state='CLAIMED' AND lease_version=:observed AND lease_owner=:owner`; zero rows = `StaleClaimNoop` (takeover happened, row already `ACKED`/`EXHAUSTED`/`PENDING`, or a duplicate of the same ACK). Lease validity (`lease_until`) is **not** part of the predicate: an unchanged version and owner means nobody took the row over, so recording a delivery fact (a real `202`, or a retry) is safe even if the lease has just expired; fencing is by `state + version + owner` (lead `CONDITIONAL APPROVAL` of D-06 @ `531805b`; the repair port and its race tests still need a TV1/TV2/TV5 freeze before implementation). Fields written:
  - `ACK` (`202`): `state='ACKED'`, `acked_at=:now`, `lease_owner=NULL`, `lease_until=NULL`, `updated_at=:now`; `delivery_attempts` and `next_retry_at` unchanged.
  - `RETRY` (timeout, connection error, 5xx, other retryable class): `state='PENDING'`, `delivery_attempts=delivery_attempts+1`, `next_retry_at=:next` (ADR-005 backoff, parameter), lease columns `NULL`, `updated_at=:now`.
  - `EXHAUSTED` (budget from ADR-005 spent, or a non-retryable class chosen by TV1): `state='EXHAUSTED'`, `delivery_attempts+1`, lease columns `NULL`, `updated_at=:now`.
  - `lease_version` is **never** reset or decreased; it only moves in `claim`. `acked_at` is set only by ACK. `dispatch_payload`, `event_id`, `attempt_id`, `event_type`, `created_at` are never in a `SET`.
  - `202 ACK` never terminalizes the Job. Backoff `2,4,8,16,30,30…` s and the repair probe at `finish_due_at + 10 s` come from ADR-005 as parameters, not constants in the port. A PAUSED Listing does not stop retrying an already-allocated event.
  - **Receipt-repair resend** (missing receipt after `finish_due_at + 10 s`) is **not** the normal claim. It needs its own explicit, separately authorized port (`claim_repair_resend`, `ACKED` only, Job still `RUNNING`, no `PENDING`/`ACCEPTED` Inbox row; TV1 designs it with ADR-005, lead ACK). Until that port is accepted, an `ACKED` row never leaves `ACKED`.

### `B-IF-07` — TV1 ↔ TV2 ↔ TV5: finalization and fallback
- `finalize_one(job_id, verified: VerifiedV1Receipt) -> Finalized(job_id) | AlreadyTerminalNoop | PrecedingPending(first_pending_cursor) | RejectedCandidate(reason) | CommitOutcomeUnknown`.
  - `VerifiedV1Receipt` is a typed value from TV3's verifier carrying, at least: `inbox_id`, `result_id`, `envelope_sha256`, `job_id`, `attempt_id`, `worker_id`, `listing_id`, `key_id`, the verdict (outcome and failure reason) and the signed fields to persist. TV2 never trusts it as proof (typed API `P2E-VERDICT-CONTRACT-01 = PENDING_ACK` with TV3 + TV5).
  - Steps: locator read; Listing → Job → Allocation lock; recheck `RUNNING`; load the Inbox row by `inbox_id` and **recheck from the database** that it is `PENDING`, `received_at < hard_deadline_at`, `verified.result_id` equals the persisted `result_inbox.result_id` (and later the `signed_results.result_id` written from it), its `bound_job_id/bound_attempt_id` equal the locked Job and attempt, `envelope_sha256` equals both the stored hash and `sha256(original_envelope_raw)`, and that `worker_id`, `listing_id` and `key_id` equal the locked Job and an existing `worker_public_keys` row of that Worker; then the earliest-winner check from B-IF-05 (`PrecedingPending`). **Admission vs processing (P1-02):** the only deadline test is on the *stored* `received_at` (`< hard_deadline_at`). `finalize_one` and `reject_candidate` never compare the current time with `hard_deadline_at`, so an on-time committed candidate is processed after a restart even when `now() > hard_deadline_at`; only new callbacks (ingress) and the SYSTEM_FAULT fallback depend on the current clock. Any mismatch, a different `result_id` included, is `RejectedCandidate(BINDING_MISMATCH)` with **zero** business effect and **no** state change (a wrong binding is a caller bug, not a verdict on the receipt).
  - One COMMIT writes `signed_results` (bytes copied from the Inbox row **in the same UoW** with `INSERT … SELECT … FROM result_inbox WHERE id = :id`, a plain `INSERT` with no `ON CONFLICT … DO UPDATE`, so a replay or reconcile never overwrites; `uq_signed_results_job_id` and the primary key enforce one result; the test asserts `signed_results.original_envelope_raw = result_inbox.original_envelope_raw` and the hash), Job terminal (`COMPLETED`, or `FAILED` with `WORKER_FAULT`/`JOB_FAULT`), allocation `RELEASED`, Listing counter `-= gpu_count`, Inbox `ACCEPTED`, and per TV5's policy the contribution (`SUCCESS`, `WORKER_FAULT`, or `NONE` for `JOB_FAULT`) plus the aggregate delta (`+1 successful` / `+1 fault` / `0`). Existing terminal Job or contribution ⇒ `AlreadyTerminalNoop`, no second effect.
  - Aggregate statement (D-11 / D-12; **only** when the category is `SUCCESS` or `WORKER_FAULT`): one `INSERT INTO worker_reputation_aggregates (worker_id, successful_jobs, worker_fault_jobs, updated_at) VALUES (:w, :s, :f, :t) ON CONFLICT (worker_id) DO UPDATE SET successful_jobs = worker_reputation_aggregates.successful_jobs + EXCLUDED.successful_jobs, worker_fault_jobs = worker_reputation_aggregates.worker_fault_jobs + EXCLUDED.worker_fault_jobs, updated_at = EXCLUDED.updated_at`, with `(s, f)` = `(1, 0)` or `(0, 1)` and `:t = clock_timestamp()` read after the locks. It is the last lock in the order, so it cannot create a cycle. For `NONE` (`JOB_FAULT`), `SYSTEM_FAULT`, a duplicate or a rejected candidate the statement is **not issued** and the aggregate row, including `updated_at`, is untouched. No invented delta or timestamp.
- `deadline_fallback(job_id) -> SystemFaultFinalized | ContinueCandidateScan(first_pending_cursor) | NotYetDue | AlreadyTerminalNoop | CommitOutcomeUnknown`. **There is no caller-supplied proof, boolean or cursor** (TV5 blocker B). Under the Listing → Job locks the port re-reads the committed state: Job `RUNNING`; `clock_timestamp() >= hard_deadline_at` (else `NotYetDue`); and `NOT EXISTS` any `PENDING` Inbox row of this Job with `received_at < hard_deadline_at`. If one exists the answer is `ContinueCandidateScan` and nothing changes. Only when every on-time row was already settled (`REJECTED` by a definitive verdict through `reject_candidate`, none `ACCEPTED`, else the Job would be terminal) does it write `FAILED/SYSTEM_FAULT`, one allocation release, one counter decrement, and **no** signed result, **no** contribution, **no** aggregate change. A transiently unverifiable row stays `PENDING` and therefore blocks fallback instead of being guessed. A rejected receipt and a missing receipt are distinguished by Inbox state.
- One atomic transaction (TV5 blocker C): signed result, terminal Job, allocation release, Listing decrement, Inbox status, at most one contribution, aggregate delta all commit together or not at all. `SYSTEM_FAULT` writes no signed result, contribution or penalty. Unknown `COMMIT` is reconciled by reading the DB. A PAUSED Listing does not block redelivery of an already `RUNNING` attempt (B-IF-06).
- The classification (what is `WORKER_FAULT`, what is `NONE`) is TV5's; TV2 executes it atomically and does not reinterpret it. TV2 never reads `simulation_references` in either port (D-14).

### `P2E-VERDICT-CONTRACT-01` — typed verdict and provenance (proposal for freeze, `PENDING_ACK`)
Producer TV3 (pure verifier), consumers TV1 (orchestration), TV2 (ports), TV5 (policy). Proposed frozen shape, to be ACKed by file SHA:
- **Provenance:** a `VerifiedV1Receipt` or `RejectedV1Receipt` (one shared name with TV3's producer contract; TV3 to confirm against its current PR #49 HEAD) can only be built by TV3's verifier (private constructor/factory); TV2 treats it as a typed carrier of *identities and the values to persist*, never as proof, and rechecks every identity from the database.
- **`VerifiedV1Receipt` fields:** `schema_version` (`'1'`), `inbox_id`, `result_id`, `envelope_sha256`, `job_id`, `attempt_id`, `worker_id`, `listing_id`, `key_id`, `outcome` (`SUCCESS`|`FAILED`), `failure_reason` (`WORKER_FAULT`|`JOB_FAULT`|null), `result_digest`, `finished_at_wire` (signed string, never used for admission), `payload_jcs_raw`, `signature_raw`. `original_envelope_raw` is **not** passed: TV2 copies it from the Inbox row in the same UoW.
- **DB recheck (B-IF-07):** `inbox_id`, `result_id`, hash, `job_id`, `attempt_id`, `worker_id`, `listing_id`, `key_id` must equal the persisted Inbox row and the locked Job/attempt/key. Any difference ⇒ `RejectedCandidate(BINDING_MISMATCH)`, zero business effect, no state change. **Derived signed parts (TV5):** `payload_jcs_raw` and `signature_raw` must correspond to the retained envelope, not only to matching ids. Two options, both pure code provided by TV3, to be chosen by TV1 + TV5 (**TV3 now accepts V-OUT**, with V-IN as fallback only, and raises erratum `E-C4` for the approved `TX-FINALIZE` pseudo-code; V-OUT matches the port signatures below): **(V-IN, not selected)** run TV3's full verifier **inside** the finalization UoW, after the locks, on the locked Inbox bytes (one Ed25519 check on at most 16 KiB, no network I/O); then the carrier does not need to ship `payload_jcs_raw` / `signature_raw` and the equality check below is unnecessary because TV2 persists what the in-UoW verification produced. **(V-OUT, approved by the lead as E-C4 @ `531805b`, current port design)** verification stays outside the locks and TV2 runs the pure extractor `extract_signed_parts_v1(original_envelope_raw) -> (payload_jcs_raw, signature_raw)` on the **locked Inbox row's bytes** and requires byte equality with the carrier's two fields before `signed_results` is inserted (mismatch ⇒ `BINDING_MISMATCH`). Extractor semantics TV3 will freeze in #49: `payload_jcs_raw = UTF-8(JCS_RFC8785(payload))` **without** the `GPU-MARKETPLACE:SIGNED-RESULT:V1\n` domain prefix (the prefix is added only for verification; `signed_results` stores the unprefixed bytes), `signature_raw` = the 64 decoded bytes of the 86-character unpadded base64url signature, same strict parser as ingress (exactly 11 fields, duplicate keys rejected). **If the extractor (or the in-UoW verifier) fails on locked bytes that ingress already accepted, that is an invariant break, not a verdict:** fail closed (`DependencyUnavailable`-like), the row stays `PENDING`, alert, no `BINDING_MISMATCH` and no rejection.
- **`RejectedV1Receipt` fields:** `inbox_id`, `result_id` (**non-NULL**: every row stored by ingress passed strict `result_id` parsing, and a receipt that fails that parsing is answered `422` before the UoW and never stored, so it never reaches `reject_candidate`), `envelope_sha256` (the hash of the bytes the verifier actually examined), `job_id`, `attempt_id`, `rejection_code` from a closed, redacted enum owned by TV3; only a **definitive** verdict may call `reject_candidate`, and the port binds it to the persisted row and hash after the locks (above). A transient failure is neither verdict and changes nothing. **Names now match TV3's PR #49 @ `942383f`** (`inbox_id` and the same identity fields, one closed reason enum). The contract is still not frozen: it needs the TV1 and TV5 ACK at the final SHAs of #46, #49 and #50.
- **Extractor constraints (TV5):** `extract_signed_parts_v1` is pure, deterministic, bounded, with no DB or network I/O and no privilege change; TV3 confirms its exact semantics (JCS payload versus original wire bytes, base64url signature decoding, strict malformed/duplicate-key JSON handling) in its producer contract. It does not replace TV3's Ed25519 verification.
- **Stale verdict:** if at finalization the Inbox row is no longer `PENDING`, or the Job is no longer `RUNNING`, the port returns `AlreadyTerminalNoop`/`AlreadyDecidedNoop` and writes nothing. A key retired after verification does not invalidate the receipt (`B-IF-08`, RESTRICT FK keeps the historical row). Under quiescent K1→K2 rotation no `PENDING` candidate signed by K1 should exist when K1 is retired; if one does, the verifier still checks it against the retained K1 row and does not reject it as `UNKNOWN_KEY`. Compromise handling stays a lead decision (D-03 / X-03).
- **Not carried:** raw envelope bytes, private material, protected-reference fields.

### `B-IF-08` — TV2 ↔ TV3 ↔ TV5: keys
`signed_results (worker_id, key_id)` FKs to `worker_public_keys ... ON DELETE RESTRICT`, so a retired key still verifies old receipts and cannot be deleted while a receipt references it. Key readiness, rotation and compromise rules are owner decisions (D-03); the DB contract here is only "historical key row exists and is referenced".

### `B-IF-09` — TV1 ↔ TV2: environment and budgets
Disposable PostgreSQL with `db_safety` markers; `restored_login_role_credentials` around any test that sets role passwords; `lock_timeout`/`statement_timeout` set per UoW (values from `RUNTIME_BUDGET.md`, none invented); bounded executor and pool; shutdown waits for the in-flight UoW to commit or roll back. Status: `PENDING_PARAMS / TEST`.

## 3. Data returned to callers (for the ACKs)

`Allocated`, `FencedClaim`, `Batch`, `Finalized` carry identifiers and timestamps only. They never carry `dispatch_payload` contents beyond what TV1 must send, raw envelope bytes, signature bytes, public key bytes or protected-reference fields.
