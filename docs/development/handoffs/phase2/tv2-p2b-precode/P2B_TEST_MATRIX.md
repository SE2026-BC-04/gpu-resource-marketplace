**Owner:** TV2 · **Status:** `PROPOSED_FOR_ACK` (TV1 + TV2) · **Date:** 2026-11-08

## 1. Rules every test follows

- Real PostgreSQL 16 on a disposable, marker-checked cluster (`backend/tests/db_safety.py`); native logins for role tests; two or more independent connections for any race, with explicit barriers (the pattern in `test_listing_submit_concurrency_postgres.py`: separate UoWs, `threading.Event` gates at lock acquisition points, both commit orders).
- Fixed UUIDv4 fixtures; before/after row snapshots; assertions on rows, not on log text.
- Time (P2-03, lead review). Two different clocks, two techniques:
  - **T-D1 (Manager business time only):** Manager UoW constructors (`allocate`, `finalize`, `deadline_fallback`, Outbox claim) take a `clock_sql` fragment defaulting to `clock_timestamp()`; only test composition passes a fixed expression; production wiring never does. Used for `started_at`, `now() >= hard_deadline_at` in fallback, lease expiry.
  - **T-D2 (Inbox `received_at`; replaces clock injection for ingress):** `received_at DEFAULT clock_timestamp()` cannot be injected and the API role must not gain a way to set it. So the stored instant is controlled by the **test harness**, never by the API role. (a) *Equality and plus/minus 1 microsecond predicate tests* use rows seeded by the owner connection (test harness only, disposable DB) with `received_at = hard_deadline_at - 1us`, `= hard_deadline_at`, `+ 1us`, and run the DB-side predicates that read stored values (candidate scan, `PrecedingPending`, fallback `NOT EXISTS`, `finalize_one` recheck). The ingress decision itself is a small pure function `is_late(received_at, hard_deadline_at) = received_at >= hard_deadline_at`, unit-tested on exact equality with timezone-aware values. (b) *Real DB-clock ingress tests with a barrier, no Python sleeps:* a holder session locks the Job row, the ingress session blocks on the lock, the holder runs `pg_sleep` until `clock_timestamp()` has passed a deadline seeded a few hundred ms ahead, then commits; the ingress then inserts after the deadline and must answer `Ineligible(late)` with nothing stored; the converse run with a far deadline must answer `Stored`. (c) *Race sweep* for `P2B-DRT-17`: many ingress attempts against a deadline a few ms ahead; either outcome is legal, but "`202` with stored `received_at >= hard_deadline_at`" is forbidden. The same sweep is TV3's `P2C-DRT-10`. If D-17 selects the `BEFORE INSERT` trigger variant, (a)-(c) still apply and the trigger is also exercised with owner-seeded and native-role inserts.
- Any test that sets role passwords uses `restored_login_role_credentials` (from #42). See `DB_TEST_ISOLATION.md`.
- Timestamps are timezone-aware; local cluster runs in `Asia/Bangkok`, CI in UTC; assertions compare instants, not wall-clock strings.
- Per-test evidence record (template at the end).

New after the TV5 cross-review (all `NOT_RUN`):
- `P2B-DRT-18` (`test_outbox_payload_postgres.py`): payload has exactly the ten keys and none of `simulation_references`, seed, expected outcome, key, token; `outbox_event_id = event_id`, `attempt_id` equal; `simulation_input` is the fixed profile; payload columns of the Outbox row are unchanged after claim / ack / retry; the raw HTTP body bytes (as sent on the wire, captured at the HTTP boundary) are identical across first claim, retry, stale-lease takeover and process restart, with the payload read from the database each time and no protected reference read; the frozen external DTO has no extra key; the types and bound values of `gpu_count`, `duration_seconds`, the Job/Worker/Listing ids and the RFC 3339 timestamps are tested in the Manager transaction / serializer (the CHECK does not validate cross-table consistency); the shape CHECK rejects 9 or 11 keys, a wrong profile, a non-object, and the NULL-predicate cases: `attempt_id: null`, `outbox_event_id: null`, a missing id key, an id given as a number, an id that differs from the column, an uppercase UUID string; timestamps in the payload parse to the `execution_attempts` column values.
- `P2B-DRT-19` (`test_finalize_postgres.py`): aggregate `updated_at` and counters change exactly once for `SUCCESS` and `WORKER_FAULT` (first finalization creates the row with +1, later ones increment; concurrent finalizations of two Jobs of one Worker end at +2) and are byte-for-byte unchanged for `NONE` (`JOB_FAULT`), `SYSTEM_FAULT`, duplicate and rejected candidates.
- `P2B-DRT-20` (`test_finalize_postgres.py`): earliest-winner under two consumers with barriers: candidate A (earlier, invalid) and B (later, valid); finalizer 2 locks first and presents B ⇒ `PrecedingPending`, no effect; after A is `REJECTED`, B finalizes; also valid-A / valid-B where B's finalizer acquires the lock first: B gets `PrecedingPending`, A (the earlier valid candidate) wins and B ends `REJECTED(NOT_SELECTED)`; batch bound = 1 and bound > number of rows both reach the same winner; the reverse commit order yields the same result.
- `P2B-DRT-21` (`test_deadline_fallback_postgres.py`): `deadline_fallback` ignores any caller claim: a committed on-time `PENDING` row present at lock time ⇒ `ContinueCandidateScan`, no write; a row inserted by ingress concurrently (barrier before / after the Job lock) is either seen or rejected as not-running; a transiently unverifiable row stays `PENDING` and blocks fallback; after all rows are `REJECTED` and `now() >= hard_deadline_at` ⇒ one `SYSTEM_FAULT`, one release, no signed result, no contribution, no aggregate change; `VerifiedV1Receipt` with a wrong `inbox_id`, hash, worker, listing, attempt or `key_id` ⇒ `RejectedCandidate(BINDING_MISMATCH)` with no state change; a `verified.result_id` different from the persisted `result_inbox.result_id` (all else equal) has zero business effect, and after a normal finalization `verified.result_id = result_inbox.result_id = signed_results.result_id`.
- `P2B-DRT-22` (`test_finalize_postgres.py`): `signed_results` bytes equal the Inbox bytes and hash after finalization; a replay and an injected unknown `COMMIT` followed by reconcile never overwrite the row; `UNIQUE(job_id)` holds.
- `P2B-DRT-23` (`test_finalize_postgres.py`): `reject_candidate` with a verdict whose `envelope_sha256` or `inbox_id` belongs to another row ⇒ `BindingMismatchNoop`, the other valid `PENDING` row untouched and fallback still blocked; swapped-field cases: `inbox_id` of B with the unchanged hash, binding and `result_id` of A ⇒ no-op; a differing `result_id`, `job_id` or `attempt_id` alone ⇒ no-op; the converse control, a self-consistent genuinely verified rejection of B while A is also `PENDING`, is **accepted** (B becomes `REJECTED`, A untouched), so a row difference alone is never labelled a mismatch; `finalize_one` with `payload_jcs_raw` or `signature_raw` that differ from `extract_signed_parts_v1` of the locked Inbox bytes ⇒ `BINDING_MISMATCH`, nothing written.
- `P2B-DRT-24` (`test_worker_key_lock_postgres.py`, D-18): allocate vs key registration barrier in **both commit orders**. Registration holds the exclusive lock first ⇒ allocate waits, then (two active keys) answers `Blocked(SIGNER_NOT_READY)`, head stays `QUEUED`, nothing written; allocate holds the shared lock first ⇒ registration waits until allocate commits, so no attempt starts after the second key is visible.
- `P2B-DRT-25` (`test_worker_key_lock_postgres.py`): two allocations for different Listings of the **same** Worker run concurrently under the shared lock (neither waits on the other); allocation of another Worker is never blocked by registration for this Worker. `lock_timeout` on the Worker lock ⇒ `Noop(LOCK_BUSY)`, rollback, no counter change.
- `P2B-DRT-26` (`test_worker_key_lock_postgres.py`): signer-ready rule: zero active keys, one active key and two active keys ⇒ `Blocked(SIGNER_NOT_READY)`, `Allocated`, `Blocked(SIGNER_NOT_READY)`; activation that would retire K1 while a `RUNNING` attempt exists aborts and writes nothing; after drain it succeeds and allocation resumes; a K1 receipt still verifies from the retained row. `Listing.worker_id` recheck: a locator/lock mismatch rolls back.
- `P2B-DRT-27` (`test_native_roles_postgres.py`, `NOT_RUN` until the native Manager and provisioning logins exist): `pg_advisory_xact_lock_shared` / `pg_advisory_xact_lock` execute as `gpm_manager_app` and as the provisioning identity without any new grant; the lock is released at transaction end (a second session acquires it after COMMIT and after ROLLBACK).
