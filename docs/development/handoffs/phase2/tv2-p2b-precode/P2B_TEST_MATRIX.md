## 1. Rules every test follows

- Real PostgreSQL 16 on a disposable, marker-checked cluster (`backend/tests/db_safety.py`); native logins for role tests; two or more independent connections for any race, with explicit barriers (the pattern in `test_listing_submit_concurrency_postgres.py`: separate UoWs, `threading.Event` gates at lock acquisition points, both commit orders).
- Fixed UUIDv4 fixtures; before/after row snapshots; assertions on rows, not on log text.
- Time (P2-03, lead review). Two different clocks, two techniques:
  - **T-D1 (Manager business time only):** Manager UoW constructors (`allocate`, `finalize`, `deadline_fallback`, Outbox claim) take a `clock_sql` fragment defaulting to `clock_timestamp()`; only test composition passes a fixed expression; production wiring never does. Used for `started_at`, `now() >= hard_deadline_at` in fallback, lease expiry.
  - **T-D2 (Inbox `received_at`; replaces clock injection for ingress):** `received_at DEFAULT clock_timestamp()` cannot be injected and the API role must not gain a way to set it. So the stored instant is controlled by the **test harness**, never by the API role. (a) *Equality and plus/minus 1 microsecond predicate tests* use rows seeded by the owner connection (test harness only, disposable DB) with `received_at = hard_deadline_at - 1us`, `= hard_deadline_at`, `+ 1us`, and run the DB-side predicates that read stored values (candidate scan, `PrecedingPending`, fallback `NOT EXISTS`, `finalize_one` recheck). The ingress decision itself is a small pure function `is_late(received_at, hard_deadline_at) = received_at >= hard_deadline_at`, unit-tested on exact equality with timezone-aware values. (b) *Real DB-clock ingress tests with a barrier, no Python sleeps:* a holder session locks the Job row, the ingress session blocks on the lock, the holder runs `pg_sleep` until `clock_timestamp()` has passed a deadline seeded a few hundred ms ahead, then commits; the ingress then inserts after the deadline and must answer `Ineligible(late)` with nothing stored; the converse run with a far deadline must answer `Stored`. (c) *Race sweep* for `P2B-DRT-17`: many ingress attempts against a deadline a few ms ahead; either outcome is legal, but "`202` with stored `received_at >= hard_deadline_at`" is forbidden. The same sweep is TV3's `P2C-DRT-10`. If D-17 selects the `BEFORE INSERT` trigger variant, (a)-(c) still apply and the trigger is also exercised with owner-seeded and native-role inserts.
- Any test that sets role passwords uses `restored_login_role_credentials` (from #42). See `DB_TEST_ISOLATION.md`.
- Timestamps are timezone-aware; local cluster runs in `Asia/Bangkok`, CI in UTC; assertions compare instants, not wall-clock strings.
- Per-test evidence record (template at the end).

- `P2B-DRT-44` (`test_native_roles_postgres.py` + `test_finalize_postgres.py`, `NOT_RUN`): `CommitOutcomeUnknown` is **raised** (typed, after the `Session` is closed) by `reject_candidate`, `finalize_one` and `deadline_fallback` when the connection is killed after `COMMIT` is sent, and the port does not resend inside the same call. Recovery per `B-IF-07A` §4: `reconcile_settlement` answers `Settled` when the first COMMIT succeeded and `NotSettled` when it did not; only after `NotSettled` is the write re-driven, with evidence reloaded and re-verified (the test asserts a fresh `load_evidence`/verify, not the stale value) and the same stable identities, giving exactly one effect; both commit orders and a restart between the steps. Allocation, Outbox and repair ports are **not** changed by this test (their `reconcile_allocation`/fencing tests stay as they are).
- `P2B-DRT-45` (`test_discovery_postgres.py` + `test_deadline_fallback_postgres.py`, `NOT_RUN`): sustained candidate arrivals. A producer keeps committing `PENDING` rows for other Jobs while Job D becomes due with no Inbox row; the cycle runs the candidate step and the deadline step every cycle, and `deadline_fallback(D)` completes once within the relation of `B-IF-07A` §3.2 (candidate-step budget + one per-operation timeout + one cycle wait, measured against the configured values, no invented number); the candidate list is never empty during the run.
- `P2B-DRT-46` (`test_deadline_fallback_postgres.py`, `NOT_RUN`): slow or unavailable dependency. One session holds the Listing lock so one candidate UoW hits `lock_timeout` (`LOCK_BUSY`); a stub verifier is slow and then unavailable. Unrelated due Jobs still reach `deadline_fallback` within the same bound, the blocked Job's row stays `PENDING`, and no step waits without a timeout.
- `P2B-DRT-47` (`test_runtime_saturation_postgres.py`, TV1 + TV2, `NOT_RUN`): pool and executor saturation. With the pool and executor slots exhausted by candidate work, a further candidate submission is refused with a transient instead of queued without bound, the capacity reserved for the deadline step is still available, and queue depth and wait are observed; no limit is asserted beyond the configured ones.
- `P2B-DRT-48` (`test_deadline_fallback_postgres.py`, `NOT_RUN`): bounded progress of unrelated due Jobs. `N` due Jobs over several pages, one blocked by a `PENDING` row, one behind a held lock; every other due Job is finalized across successive passes in `(hard_deadline_at, job_id)` order, the two blocked Jobs are reached again on the next pass, and no Job is skipped forever.
- `P2B-DRT-49` (`test_runtime_saturation_postgres.py`, TV1 + TV2, `NOT_RUN`): cancellation and worker ownership. Cancel the task awaiting a running synchronous port call: the SQL statement either completes or ends at `statement_timeout`, the owning task waits for it, `engine.dispose()` runs only after that, no second call starts on the same `Session`, and the outcome of a call cancelled after `COMMIT` is recovered with `reconcile_settlement`.
- `P2B-DRT-50` (`test_finalize_postgres.py`, `NOT_RUN`): `reconcile_settlement` identity and contradiction. Complete graphs for `FINALIZE`, `REJECT` and `FALLBACK` answer `Settled`; a Job terminal through another winner or the fallback answers `SettledOther`; a still-`PENDING` row of a `RUNNING` Job answers `NotSettled`; seeded partial or contradictory graphs (Inbox `ACCEPTED` without signed result, terminal Job with allocation not `RELEASED`, signed result for another `result_id`, another `attempt_id`/`inbox_id`) answer `SettlementUnknown` and the caller fails closed with no write.
